Balance Component Contingent / Off-Balance-Sheet Exposure Account-Entry Requirements Review

Contingent Liability Ledger

Dr/Cr account-pair requirements for every Import LC and Export Confirmed LC contingent-liability scenario in scope for the Balance Component, drawn strictly from the project's own design specifications.

Scope boundary — read before the tables

The Balance Component owns contingent / off-balance-sheet exposure only. Every pair below is a memorandum entry that never touches a financial-statement line. On-balance-sheet legs — the funded receivable an Honour creates against the applicant, the accounting Acceptance/DPU liability itself, cash margin, commission, ECL provisioning, settlement and nostro — are explicitly out of scope and omitted from every table, even where the source document books them in the same unit of work.

In scope (shown below)

  • LC Contingent Liability — Customers' Liability / Documentary Credits Outstanding
  • Shipping Guarantee Contingent Liability — Customers' Liability / SG Outstanding
  • Confirmation Contingent Liability — Confirmation Exposure / Confirmation Outstanding
  • Acceptance & DPU shadow memo pair (Import + Export) — reporting shadow, not the accounting record

Out of scope (never shown)

  • Import Bills Receivable, Import Usance Financing/Receivable — on-BS assets
  • Acceptances & DPU Outstanding, Confirmed Acceptances & DPU Outstanding — the real on-BS liability
  • Acceptance Reimbursement Receivable (Applicant / Issuing Bank), Due from Issuing Bank — on-BS assets
  • Cash margin, unearned commission, ECL provision, settlement payable, nostro/vostro
Notation Where an event's Dr/Cr shape is identical across tenors, the applicable Tenor Types are listed once and [Tenor] stands in the account name as a literal substitution — the source document's own convention (Lifecycle spec §3.2, §3.9, §7.2, §7.7), adopted here rather than inventing a new shorthand. Applies to Folios 1 and 4, where the account itself is tenor-suffixed; Folios 2, 3 and 5 use accounts that don't vary by tenor at all, so no placeholder is needed there.

Classification note. Once the bank accepts the draft or incurs the DPU, the exposure leaves the contingent book entirely — it becomes a present, unconditional financial liability under IFRS 9, on-balance-sheet, matched by an on-balance-sheet reimbursement receivable. Neither leg is shown here. The pair below is the reporting shadow memo the source document prescribes for MIS/MT reconciliation only — never the accounting record, and never itself a true contingent balance type. Balance Component's own domain model reflects this: an Acceptance movement is tagged exposureNature = ACTUAL, not CONTINGENT. Covers A6 (Create leg), A7.

Implementation notes

  1. Amendment Decrease is gated on beneficiary consent in the source document (UCP 600 Art. 10(a)/(c) — no balance movement until consent is recorded). Balance Component's own AMEND_DECREASE movement books immediately on Maker submission with no consent-workflow gate; the account pair itself is unaffected.
  2. Document/Presentation receipt is a genuine lifecycle event with no contingent GL effect — an operational memo only, under both Design Principle D3 ("documents arriving is a physical event... only legal events move balances") and the source document's own MEMO_ONLY classification. Shown here as its own row, rather than omitted, specifically so A3 (Import) and B3 (Export) are visibly accounted for rather than silently absent from Folio 1/4.
  3. Sight Honour is modelled as a single Utilize-then-Release step in Balance Component (A3/A3S create the PENDING earmark; A4's Checker Release both finalizes it and posts this reversal). The source document's own worked example additionally distinguishes "paid under reserve / against indemnity" as a separate, non-honour path with its own account pair — not modelled in Balance Component today.
  4. Expiry / cancellation is a defined requirement, not yet an implemented function. The source document treats an unreleased residual as a required reversal on every in-scope product (LC, Confirmation). Balance Component's current movementType sets (IPLC_LC: ISSUE/AMEND_INCREASE/AMEND_DECREASE/UTILIZE; EPLC_CONFIRMATION: ISSUE/AMEND/HONOUR/ACCEPT) carry no EXPIRE or CANCEL value — this row documents the required pair, not a callable Transaction Builder function.
  5. Buyer's Usance funding-party split (BU-A self-funded vs. BU-B refinancing-bank-funded) only affects the on-balance-sheet asset the Honour creates — both variants reverse the identical contingent pair shown here. Balance Component does not model the BU-A/BU-B distinction at all (no fundingParty field); the merged Honour row applies to both.
  6. Seller's Usance Honour and Acceptance creation are one business action (Folio 3's own Create row fires in the same Checker compound as Folio 1's Honour release — A6's "one Release does both", per the Balance Component decision log). Shown in two folios because they post to two different account pairs; Folio 1's merged Honour row covers all three tenors, but only the Seller's Usance case additionally triggers Folio 3.
  7. SG Issue and an SG amount increase post the identical Dr/Cr pair — Dr Customers' Liability under Shipping Guarantees / Cr Shipping Guarantees Outstanding, same direction, same accounts. Balance Component has no distinct AMEND movementType for SHGT at all (its implemented set is ISSUE/PARTIAL_REDEEM/FULL_REDEEM only) — unlike LC/Confirmation, there is no A-series function for "SG Amendment" in the Transaction Builder registry. A genuine increase in guaranteed coverage is realized as another SG Issue (A8), not a separate amendment event, so the row above covers both and is labelled accordingly rather than as a distinct, uncoded "Amendment — Increase". A genuine amount Decrease and a Claim under the SG are different in kind — they move the pair in the opposite direction from Issue and have no Balance Component equivalent at all today, not even a practical A8/A9 workaround; both remain source-document-only requirements.
  8. Partial SG redemption is a confirmed, deliberate divergence from the source document, and applies identically to A9 and to A3S's own SG leg. Both call the same domain redemption logic (shgtRedeem.ts), deriving FULL_REDEEM vs. PARTIAL_REDEEM from the same MIN(Bill Amount, SG Outstanding) calculation — A3S is not a separate rule, just a second caller of it, triggered as the first of its two linked legs (see Folio 1's own Honour row and the Function Code Coverage index above). §4.4 of the Lifecycle spec explicitly rejects a MIN(document amount, SG outstanding) partial-release rule as a permanent, growing overstatement of the off-BS book, and prescribes an all-or-nothing, two-stage (REDEEMABLE → RELEASED) discharge instead. Balance Component ships the MIN()-based partial redemption the source document argues against, per an explicit later business instruction (2026-08-15) overriding the original design. Documented here as a known, business-confirmed choice — not an oversight.
  9. Import Acceptance under Buyer's Usance is a further, related divergence. The source document's own derivation matrix routes Buyer's Usance honour to LC_HONOUR_BU_A/LC_HONOUR_BU_B directly — no Acceptance/DPU instrument is created under true Buyer's Usance at all; only Seller's Usance (availability = ACCEPTANCE or DEF_PAYMENT) fires LC_ACCEPT. Balance Component's own A6 function offers both Buyer's and Seller's Usance as tenor options for creating an IPLC_ACCEPTANCE record, and does not distinguish their downstream accounting treatment. The Buyer's Usance row in Folio 3 documents what the current implementation actually does, flagged against the source document's stricter separation.
  10. Export tenor collapse (Sight/BU/SU → Sight/Usance). B4's own movementTypeFromContractTenor derives HONOUR for a Sight-tenor Confirmation and ACCEPT for anything else — it does not distinguish the source document's own §7.5 "Case 1" (Buyer's Usance honoured at sight, no Acceptance) from "Case 2" (Buyer's Usance honoured by acceptance/deferred payment, Acceptance created). Every non-Sight Confirmation in Balance Component is treated as the Acceptance-creating path — which is why Folio 4's own Tenor Type is only ever Sight or Usance, never a three-way split.
  11. Confirm LC Amendment has no direction sub-choice. Balance Component's B2 uses one fixed AMEND movementType for both increase and decrease (signed delta), unlike the Import side's separate AMEND_INCREASE/AMEND_DECREASE. Both directions are shown as the same event code with the Dr/Cr sides swapped for the decrease case — matching Folio 1's own A2 treatment so the two products stay directly comparable.
  12. Usance Accept is the same compound action as Folio 5's own Create row — B4's Usance branch releases Folio 4's Confirmation pair and creates Folio 5's shadow-memo Acceptance pair together, one Checker Release. Folio 4's merged row covers Sight and Usance together; only the Usance case additionally triggers Folio 5.
  13. Held-to-maturity and pre-maturity discounting reverse the identical shadow-memo pair. The source document's own §7.6 gives them separate worked entries (Step 2a vs. 2b) because the on-balance-sheet treatment differs — the discounted claim reclassifies rather than settling in cash. Balance Component's B5 does not distinguish the two (both are FULL_SETTLE/PARTIAL_SETTLE); the contingent-scope reversal shown is correct for either.
