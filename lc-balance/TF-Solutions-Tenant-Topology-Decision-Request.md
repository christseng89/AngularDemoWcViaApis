## 背景（30 秒版）

Balance Component 微服務目前的資料模型是**單一全域命名空間**——沒有任何欄位標示「這筆 LC/SG/Acceptance
合約屬於哪個分行或哪家銀行」。這件事本身不是 bug，是因為目前只有一個內部呼叫方（Angular 參考實作）。

問題出在：如果要把這份 API 正式開放給 **TF Solutions** 整合，這個「單一命名空間」的假設會不會需要
打破，直接決定了接下來要做的工程範圍差非常多。

## 請回答的問題

**TF Solutions 這次的整合，是對接單一機構，還是需要對接多家分行/多家銀行？**

（如果現階段還沒有明確答案，「目前只確定是單一機構，未來 12 個月內沒有多機構計畫」也是一個可以接受的
明確答案——重點是要有一個現在可以依據的結論，而不是留白。）

## 這個答案會決定什麼

| 回答 | 對 OAS-GAP-09 的影響 | 對應工程範圍 |
|---|---|---|
| 單一機構，且短期內無多機構計畫 | 降級為 P1，甚至延後到第二個外部串接方出現時再處理 | 這次只需要做 OAS-GAP-01（認證），不用同時設計租戶隔離模型；範圍小很多 |
| 需要對接多家分行/多家銀行 | 維持 P0，跟 OAS-GAP-01 併同一輪決策 | 認證 + 租戶隔離模型要一起設計，且需要規劃 Angular UI／Business Case Runner 這兩個既有內部呼叫方的同步改造（見提案文件「落地衝擊：現有內部呼叫方」一節） |
| 不確定，需要評估 | 建議先以「單一機構」的最小範圍開工，租戶隔離設計成日後可擴充但不強制的欄位（例如加一個可選的 `ownerEntityId`，先不強制要求、不做查詢層過濾） | 中間路線，日後多機構需求出現時改動範圍較小，但不是現在就把隔離邏輯做完整 |

## 不在這次決策範圍內的事

這次只需要回答「單一 vs 多機構」這一個問題，不需要當場決定：
- 租戶隔離的具體技術方案（欄位設計、API Gateway 路由 vs 應用層過濾）——這是後續工程設計階段的事
- 認證機制的選型（mTLS／OAuth2／API Gateway 簽章）——OAS-GAP-01 的範圍，需要另外找資安側確認
