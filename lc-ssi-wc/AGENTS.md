- Apply Four-eyes separation of duties to every controlled rule, TDD, OAS/page-parameter contract, DB seed/fixture, QA evidence, and release decision: record a distinct Maker and Independent Checker; authors must not approve their own work.
- Before answering questions about, designing, or changing any SSI-related file-maintenance lifecycle behavior, read `memory/ssi-maintenance-workflow-memory.md` and preserve its latest-confirmed decisions. This applies product-wide to SSI, RMA, Entities, Nostro, SWIFT Data and shared maintenance UI. Do not infer a replacement workflow from a later bug report without reconciling it with that record.
- Before answering questions about, designing, loading, deduplicating, or changing RMA data, indexes, Message Type selection, lifecycle, or audit presentation, also read `memory/rma-index-message-scope-memory.md`. The governed parameter source—not UI hard-coding or raw loaded data—defines the supported MT／MX catalogue.
- Product-wide SSI-related maintenance close standard: `×` or `Esc` means Cancel; do not render a separate Cancel button. New unsaved input is discarded locally. If the workflow acquired a server-side WIP reservation, `×` or `Esc` must cancel that WIP on the server and release the lock; failure must remain visible and fail closed.
- Every state-changing maintenance workflow must implement server-authoritative concurrency control. Revise selection must atomically re-check lifecycle state, reject existing DRAFT or unexpired WIP, record a distinct WIP reservation, release it when the editor is closed with `×` or `Esc`, convert it to DRAFT only on Save Draft, and expire abandoned WIP according to the environment-configured TTL. UI button visibility is presentation only and must never be the sole concurrency control.
- Checker and QA approval must cover the same file/code SHA, TDD SHA, DB logical snapshot, build, scanner run, and evidence manifest. Any relevant change invalidates the prior approval and requires re-check.
- Include an independent DBA/Database Performance Engineer when data volume, SQL, indexes, WAL/locking, or latency is affected. Operational API, QA automation, and Browser UI must share the same versioned seed, fixture bindings, eligibility projection, and logical snapshot; database-side filtering/join/sort plus cold/hot latency and query-plan evidence are mandatory gates.
- Staffing or concurrency limits never waive Four-eyes or the independent QA gate; reserve review capacity or pause an engineering workstream instead of substituting self-review.
- TDD is mandatory for every feature and bug fix: preserve Red evidence, implement the minimum Green change, Refactor, then run affected tests, regression, and the standard `npm run verify`; never add tests only after production code or weaken assertions to obtain PASS.
- During Refactor, remove proven dead or superseded code, configuration, flags, fixtures, and test helpers. Prove deadness with reference, contract, migration, compatibility, and affected-test checks; never remove compatibility, rollback, evidence, or controlled-test behavior merely as cleanup.
- Keep one product-wide UI language: equivalent workflows must reuse the same field order, grid placement, labels, default-value behavior, action placement, loading, empty, and error states. Differences must come from governed OAS/page-parameter metadata through shared components, never Message-specific templates or CSS.
- Treat Angular performance as a two-level architecture rule: every Route／Business Feature must use route-level lazy loading (`loadComponent` or `loadChildren`) before page-level optimization; within a loaded feature, defer only heavy, optional, non-first-screen standalone UI with `@defer`. Data loading must follow the same feature boundary and must not run from the application shell for features the user has not entered. Every lazy-route transition and `@defer` loading phase must render the same shared accessible spinner/loading pattern, reserve layout space, and honor reduced-motion; do not create feature-specific spinners.
- Treat this product as an SSI Resolution microservice, not an MT/MX message-entry system: expose only the minimum human inputs that can change SSI routing or governance. Supply message/NVR/sequence/provenance test context through governed hidden scenario fixtures, and populate lookup companion IDs/versions automatically without listing them as user inputs in the workbench or index.
- For every visible user-provided SWIFT SSI field, render `SWIFT <Tag+Option> • <Official Tag Description>` from governed OAS/page-parameter metadata. Use clear business labels for non-SWIFT resolution context, and never hard-code per-message tag descriptions in UI templates.
- Evolve every Message Index additively: an `INPUT FIELDS` column must preserve all existing columns and interaction contracts, display compact Tag/Option only, and share the same governed metadata source as the Workbench; the Workbench retains the full Tag/Option plus Official Tag Description label.
- Use one governed eligibility contract, complete resolution context, and logical snapshot identity for Counterparty Picker and Resolve SSI. Every enabled candidate must be executable while context is unchanged; exclude or explicitly mark unavailable candidates before selection, and fail closed with a structured stale/unavailable reason if eligibility changes.
- Derive each Message Family/Scenario's SSI-relevant decisions from applicable SWIFT MRG, NVR, and governed SSI sources; use ISO 20022/CBPR+ usage or mapping documents only for approved MT-to-MX scope, and record MT347 as N/A with a reason. Preserve version/page-or-rule/SHA traceability. `IN_SCOPE_SSI_TAG_NVR` may block the SSI release when evidence is missing; `OUT_OF_SCOPE_FULL_FIN_NVR` is always `OUT_OF_SCOPE — CLOSED` with `FIN_VALIDATION=NOT_EVALUATED` and belongs only to an independent downstream validator workflow.
- Apply SWIFT source precedence consistently: use SR2026 when the corresponding rule or artifact exists; use SR2025 only for a documented missing SR2026 item required by a controlled customer/channel/third-party MT-to-MX converter profile. Never use SR2025 to override an explicit SR2026 deprecation, prohibition, or changed rule, and record the release, artifact SHA, converter profile, and fallback reason.
